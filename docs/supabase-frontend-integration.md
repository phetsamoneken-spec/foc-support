## Implemented

- `VITE_DATA_BACKEND=supabase` selects Supabase at build time. Development defaults to the existing GAS path. GitHub Pages now explicitly builds the Supabase variant when this branch eventually reaches main. Browser settings cannot change the selected backend.
- Pinned supabase-js 2.118.0, public project URL and publishable key only. No secret/service key, default passwords, signup UI, auto-created Admin profile or username-only login. Supabase login uses the account's email and password; legacy usernames remain display labels. Password recovery and invitations require Auth configuration and verified recipient details.
- Real Auth `getUser` validation followed by one RLS-protected atomic `mkt_snapshot` query for active profile, scoped business rows, derived financial view, profiles and audit. The JSON snapshot avoids REST row-limit truncation and mixed-revision parent/child reads. Old account/logout responses cannot restore visible data or replace accepted version tokens.
- Customer create/edit/delete, Admin condition changes and contract creation, explicit first-period budget initialization, selected-period budget creation/editing, transaction addition, Admin exception approval with reason, and cancellation map to the checked database operations. `mkt_batch` runs compound operations atomically; every sub-operation retains its receipt/version checks. Team users can register their own basic customers; Admin adds contracts, conditions and initial budgets separately.
- Admin initializes missing annual periods with an explicit amount; B1–B7 edit only their own existing periods. Missing budgets remain missing. No quantity/price formula, automatic later-year budgets, propagation of annual edits, source-money import or demo reset occurs in Supabase mode.
- Writes persist exact operation IDs/payloads/versions under project + Auth UUID before sending. A lost response remains retryable. Confirmed SQL rejection rolls back the batch. PT409 refreshes data and requires a new user submission. Local-only financial mutation and GAS account/import/publication paths are blocked in Supabase mode.
- Business data stays in memory and is cleared on logout/account change; it is not persisted into legacy GAS cache keys. Unresolved Supabase operations remain under their original owner. Legacy caches and GAS outboxes stay intact and are never replayed into Supabase. Only UI language/theme preferences persist separately. The service worker caches app assets/fonts, not Auth/REST responses.
- Admin account/config/import controls show a Supabase-specific panel rather than misleading GAS or local-success actions. Account provisioning/role assignment, shared configuration writes and validated bulk import still require trusted administration; these features are not replaced with direct client writes.
